# 知识卡片：Git 的三种合并方式

> 来源：samples/technical_git.md ｜ 卡片数：4

## 卡片 1：merge 保留历史、最安全
- **核心知识**：`merge` 创建一个合并提交把两条分支历史相连，不改写已有提交。
- **简明解释**：因为它不改写历史，所以非常适合公共分支；代价是历史里会出现分叉和合并节点，时间线较乱。
- **例子或自测问题**：自测：为什么说 merge 比 rebase 更适合已经推送到远程的公共分支？

## 卡片 2：rebase 得到线性历史但有风险
- **核心知识**：`rebase` 把当前分支提交搬到目标分支最新提交之后，形成线性历史，但会改写提交哈希。
- **简明解释**：历史更干净易读，但改写哈希意味着不要把它用在别人可能基于其工作的已推送提交上。
- **例子或自测问题**：自测：为什么"已推送到远程、他人正在使用"的提交绝对不能 rebase？

## 卡片 3：squash 在 PR 中压缩为一個提交
- **核心知识**：`squash` 把一组零散提交压缩成单一提交再合并，通常用在 Pull Request 中。
- **简明解释**：主分支上每个功能只留一个干净的提交，方便日后回溯与审查。
- **例子或自测问题**：例子：一个功能有 12 个"fix"小提交，用 squash 合并后主分支只增加 1 个提交。

## 卡片 4：按"安全 vs 干净"的取舍选择方式
- **核心知识**：选 merge、rebase 还是 squash，取决于你更看重安全的记录还是干净的记录。
- **简明解释**：merge 不改写历史最安全；rebase 改写历史需谨慎；squash 相当于给功能做个总结。
- **例子或自测问题**：自测：如果团队要求主分支历史绝对线性，你会倾向用哪种方式？
