# 理解 Git 的三种合并方式

在团队协作中，把分支合回主分支有好几种做法，理解它们的区别能让你更从容地管理历史。

Git 的 `merge` 会创建一个新的合并提交（merge commit），把两条分支的历史连起来。它的好处是不会改写已有的提交，因此很安全，特别适合公共分支。缺点是历史里会出现很多分叉和合并节点，时间线看起来比较乱。

`rebase` 则是把当前分支的提交"搬"到目标分支的最新提交之后，形成一条线性的历史。这让提交记录非常干净、易读。但 rebase 会改写提交的哈希，所以绝对不要用它去动已经推送到远程、别人可能基于它工作的提交。

第三种是 `squash`，通常在 Pull Request 里使用：把一组零散的提交压缩成一个提交再合并。这样主分支上每个功能只留下一个干净的提交，方便以后回溯。

另外补充一点：`merge` 因为不改写历史，所以最安全；`rebase` 改写历史所以要谨慎；`squash` 则像是给功能做了个总结。说到底，选择哪种方式取决于你更想要安全的记录还是干净的记录。
